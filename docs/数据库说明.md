# ailovemoney 数据库说明

日期：2026-08-30  
数据库：本机 MySQL `ailovemoney`（公开站只读运行时表和快照，不从浏览器写采集表）

本文对照当前表清单，说明每张表做什么，以及 **采集** 与 **清洗合并入库** 分别写哪些表。采集程序（`python -m scripts.crawlee_collection collect`）和 merge/import（`merge-once` / `worker`）共用这些表，不再另建平行 schema。

## 数据流

```text
采集（只写 raw）
  collection_batches / collection_runs
  -> collection_raw_payloads   （来源页面原文，审计用，约 30 天过期）
  -> collection_raw_records    （统一白名单字段，一条报价一行）

清洗合并入库（读 raw，写运行库，入库即发布）
  读 collection_raw_records（status=raw_completed 的 batch）
  -> 按稳定键、来源优先级、24 小时新鲜度合并
  -> shop_sites / shop_products
     gateway_sites / gateway_model_coverage
     official_prices
     model_leaderboards（当前 PriceAI 三页不采集排行）
  -> public_snapshot_entries   （公开页优先读的快照）
```

采集不得写运行时表或 `public_snapshot_entries`。merge 不得再发采集 HTTP。

## 采集写入哪些表

新 CLI「采集卡网 / 官方 / 中转」一次成功 run 会写：

| 表 | 作用 |
|---|---|
| `collection_batches` | 一次采集批次。完成后 `status=raw_completed`，merge 后变为 `imported` |
| `collection_runs` | 批次内每个来源一次 run。截图中的 `run-20260829…` 就是这类 ID |
| `collection_raw_payloads` | 该次抓到的完整公开 HTML/JSON，只做审计，不进 Git |
| `collection_raw_records` | 解析后的统一 raw 行（`shop_product` / `official_plan` / `gateway_site`） |

可选、不由本次 PriceAI 采集按钮自动写：

| 表 | 作用 |
|---|---|
| `collection_sources` | 旧 GUI 来源登记。新 Crawlee 来源写在代码 allowlist + `catch.config`，可不写此表 |
| `console_activity_logs` | 旧总控台操作日志 |

采集 **不写** 下面「运行库」各表，也 **不写** `collection_staging_observations`。

## 清洗合并入库写哪些表

GUI「入库」或 `merge-once` / `worker --loop` 只处理 `raw_completed` 的 batch，按 `record_kind` 写入：

| 采集记录类型 | 写入的运行时表 | 同时刷新的快照 key |
|---|---|---|
| `shop_product`（卡网） | `shop_sites`、`shop_products` | `shop-products`（及打包快照） |
| `gateway_site`（中转） | `gateway_sites`、有模型名时再写 `gateway_model_coverage` | `gateway-sites`、`gateway-models` |
| `official_plan`（官方） | `official_prices` | `official-prices`、`official-price-catalog` |
| `model_rank`（排行，现未采） | `model_leaderboards` | `model-leaderboards` |

另外会更新：

| 表 | 作用 |
|---|---|
| `collection_batches` | `status=imported`，raw 行打 `merged_at` / `imported_at` |
| `public_snapshot_entries` | 公开页读取用的 JSON 快照。**入库事务提交 = 发布** |

merge 会跳过 `collection_manual_overrides` 里锁定/隐藏的稳定键，但 raw 仍保留。

当前 PriceAI 实采：卡网进 `shop_*`，官方进 `official_prices`。中转页若解析不到站点 homepage，则只有 raw payload、没有 `gateway_sites` 新行。

## 不参与采集/merge 的表

这些表给目录、搜索、样例种子或旧流程用，**不是**「采集按钮 → 入库按钮」的目标：

| 表 | 作用 |
|---|---|
| `catalog_products` | 权威 SKU 目录（slug、平台、类型、别名），卡网聚合默认视图用 |
| `catalog_plan_models` | 官方套餐 slug 到模型族的关系 |
| `catalog_unknown_aliases` | 未能映射到目录的别名，待人工确认 |
| `shop_site_model_coverage` | 卡网站点覆盖的模型族（目录/展示，非本次 PriceAI merge 写入） |
| `shop_search_terms` | 公开搜索词统计，网站查询时累加 |
| `gateway_model_prices` | 中转站模型价明细；当前 merge 只写覆盖，不写此价表 |
| `reference_data_sources` | 公开参考样例的溯源（`pnpm run seed:reference-samples`） |
| `collection_staging_observations` | **唯一旧 staging 兼容表**。新 raw→merge 流程不再双写 |
| `collection_legacy_recovery_backups` | 纠偏旧「直发运行时」时的备份 |
| `collection_manual_overrides` | 手工锁定/隐藏稳定键，拦 merge，不拦 raw |

## 和 GUI 按钮的对应

| 按钮 | 写哪些表 |
|---|---|
| 采集卡网 / 官方 / 中转 | `collection_batches`、`collection_runs`、`collection_raw_payloads`、`collection_raw_records` |
| 入库卡网 | 读上述 raw → `shop_sites`、`shop_products`、`public_snapshot_entries` |
| 入库官方 | 读 raw → `official_prices`、`public_snapshot_entries` |
| 入库中转 | 读 raw → `gateway_sites`（及覆盖表）、`public_snapshot_entries`；无有效解析行则不新增运行时行 |

公开页面 `/shops`、`/official-price`、`/llm-gateway` 优先读 `public_snapshot_entries`，而不是直接扫 raw 表。

## 公开快照 JSON（暂用，待以后处理）

2026-08-30 问答摘要。当前仍按此运行，不改为磁盘/静态 JSON 权威源；Navicat 可见性和列类型（json → LONGTEXT）以后另开任务。

- **快照是什么：** `public_snapshot_entries` 一行一个 `key`（如 `gateway-sites`、`shop-products`）。JSON 在同表 **`payload` 列**（MySQL 5.7 类型 `json`），不是单独文件，也不是 `key` 字段里的长文本。
- **Navicat 为何像只有两列：** 数据网格常把 `json` 列藏掉，只剩 `key`、`updated_at`。数据仍在。可 `SELECT \`key\`, CAST(payload AS CHAR), CHAR_LENGTH(CAST(payload AS CHAR)) FROM public_snapshot_entries;` 或「设计表」看 `payload`。不要用 `TEXT`（64KB 上限，卡网快照已约 6 万字符）；若改类型只能 `LONGTEXT`。
- **入库时「发布 JSON」实际做了什么：** 同一事务里先写运行时表，再按种类整表 `SELECT`，在内存拼成大 JSON，`upsert_snapshot` 写入对应 `key` 的 `payload`。提交成功即发布。没有解析出的种类（如中转 `GATEWAY_SITE` 为空）不会重建该类快照，页面仍用旧 JSON。
- **网站不是前端直接查库：** `/llm-gateway` 由 Astro **服务端** `loadGatewaySites()` → `SELECT payload WHERE key='gateway-sites'`，渲染 HTML 再给浏览器。加载更多走 `/api/llm-gateway/sites.json`，仍是 Node 查库。浏览器不持有 MySQL 账号。
- **为何暂不改成磁盘/静态 json：** 预拼 JSON 是对的；权威源放 MySQL 是为避免「库新、文件旧」的第二发布路径。单次读约数万字符由服务端完成，并有 CDN/缓存头。以后若体积变大，优先分页 API 或入库事务里**额外**落运维文件，网站仍以表为准。不把运行数据提交进 Git。
