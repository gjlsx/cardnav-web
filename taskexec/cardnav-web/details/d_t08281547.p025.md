# p025 Multi-source batch and unified raw-data schema correction

## Fix sources

`FIX:t08281547.p012,t08281547.p013`

## Work

Replace the legacy per-source `raw -> staging -> public` behavior with a local collection batch. A manual collection can select one or several sources; all selected source runs receive one `batch_id`. Source raw payloads/records remain independently auditable, while collection only performs the simple normalisation required to write the project's one unified raw-record format.

Use only add-only, repeatable MySQL migrations. Define `collection_raw_records` as the one project-wide, source-neutral original-data format and extend it with `batch_id`, stable record key, source provenance, canonical product/site fields, known runtime-mapping fields, nullable optional values, validation state, and source record hash. The normalised raw schema must be a superset of the public runtime-table requirements, not a copy of any single source response. Keep `collection_staging_observations` as the only legacy staging table for compatibility/inspection; do not write it from the new collector, do not create `collection_staging_records`, do not delete samples or manual rows, and do not store credentials/cookies/full third-party HTML.

Refactor capture APIs so a source action returns a raw-complete batch/run result rather than `published`. Raw persists first for every returned source response. Invalid/unmapped raw rows are retained with a visible reason. Existing fixture/dry-run behavior stays offline unless a source is approved with an exact allowlist; approved real HTTP still targets local MySQL only. This task must not call merge/import, update entity tables, or update `public_snapshot_entries`.

## Acceptance

- Tests cover two or more sources in one batch writing the same fixed raw format with different source labels, sparse/null optional fields, valid stable keys, invalid/unmapped retention, and manual-lock raw retention.
- A collection batch stores raw provenance for every selected source without changing merge/runtime/formal tables or snapshots.
- The raw-format migration is idempotent; existing legacy staging reads remain compatible and no second staging table exists.
- No collection source-priority code reads or writes `site.score`.
