# p025 Multi-source batch, merge candidate, and schema correction

## Fix sources

`FIX:t08281547.p012,t08281547.p013`

## Work

Replace the legacy per-source `raw -> staging -> public` behavior with a local collection batch. A manual collection can select one or several sources; all selected source runs receive one `batch_id`. Source raw payloads/records remain independently auditable, while cleaning/merge treats eligible candidates from the whole batch together.

Use only add-only, repeatable MySQL migrations. Keep `collection_staging_observations` as the only staging table. Extend the existing run/staging metadata and add only the smallest batch/decision metadata necessary to show: batch identity/status, candidate record key, merge selection/rejection reason, winning source, and field provenance when a lower-priority record fills a missing field. Do not create `collection_staging_records`, do not delete samples or manual rows, and do not store credentials/cookies/full third-party HTML.

Implement a deterministic local merge service:

1. Raw persists first for every returned source response.
2. Apply the stable-key manual override before staging; locked/hidden keys are counted as skipped and never form a candidate.
3. Validate and normalise candidates, grouping every eligible candidate in the same batch by `record_key`.
4. Choose the source layer in this order: own API, own public HTML, PriceAI, CardNav, OpenPrice. A lower layer may only fill null/unknown fields. For equally ranked valid price candidates, choose the lower numeric price. Invalid/unmapped records are held with a visible reason, never silently published.
5. Persist a merged, pending-review winner view/state for every group plus non-winning provenance. No call in this task may change entity tables or `public_snapshot_entries`.

Refactor capture APIs so a source action returns a pending batch/run result rather than `published`. Existing fixture/dry-run behavior stays offline unless a source is approved with an exact allowlist; approved real HTTP still targets local MySQL only.

## Acceptance

- Tests cover two or more sources in one batch for: priority winner, lower-priority blank-field fill, equal-priority lower-price winner, invalid candidate hold, and manual lock/hide skip.
- A collection batch stores raw provenance for all selected sources and exposes pending merged candidates without changing formal tables/snapshots.
- Existing one-staging-table migration remains idempotent and old fixture reads remain compatible.
- No source priority code reads or writes `site.score`.
