# p026 Explicit formal publisher and bounded legacy-data recovery

## Fix sources

`FIX:t08281547.p013,t08281547.p016,t08281547.p019`

## Work

Create the only permitted formal-data transition: `publish_batch(batch_id)`. It accepts only a completed, locally merged pending batch, re-checks manual locks/hides and quality states inside one transaction, then updates the existing entity tables and complete `public_snapshot_entries` snapshot. Capture, dry-run, source test, source loop, and merge must not invoke it.

The API/CLI must require an explicit `publish` action and return a count/status suitable for the desktop button. It must be idempotent for a batch, reject incomplete/unknown batches, and record an activity/audit event without storing secrets. It must preserve current public data if the transaction fails.

Before changing records, implement a diagnose-first recovery command/report for formal rows created by the legacy direct-publish collector. The automated repair may touch only records that are provably legacy collector/fixture data by recorded run/source provenance; it must back up those bounded rows locally and rebuild their snapshots from the last explicitly published batch. Any ambiguous row must be listed for human review and left untouched. Never clear the whole `ailovemoney` database and never alter user sample/manual rows.

## Acceptance

- Tests prove formal tables/snapshots remain byte-for-byte/row-count unchanged after capture, loop, dry-run, test, and merge.
- Tests prove only explicit `publish_batch` updates formal data and that retrying it is safe.
- Tests cover a lock/hide added after merge but before publish; it is skipped at publication time.
- Local MySQL recovery test proves only known legacy collector rows are backed up/rebuilt; ambiguous/user rows remain intact.
