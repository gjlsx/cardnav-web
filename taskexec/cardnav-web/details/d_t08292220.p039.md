## 对比结论

- 采用 Likeshop 的做法：列出项目权威入口/架构文档，区分长期决策、taskexec 任务证据和临时调试信息；要求本地入口验证。

## CardNav 专用规则

1. 当前采集架构来源：`docs/data-nav-and-collection.md`、`docs/collection-data-lifecycle.md`、`docs/collection-capture-engine.md`、`scripts/collection/README.md`；实际改动前先读相关文档，再以源代码和测试核实。
2. 任务执行、锁、提交、状态字段和 archive 的权威规则仍是根 `.agent-rules.md`、`tasklist_rules.md` 和 `taskexec/cardnav-web/`；AGENTS 不复制表格格式。
3. 采集必须遵循 raw-first、批准来源/精确 allowlist、独立 merge/import 和本机 MySQL 边界；不得直接写运行时库、绕过挑战/验证码、在生产服务器运行采集器，或因失败清空既有公开快照。
4. 采集和网站变更需保留一行 CLI 可复现入口；浏览器可见页面须通过实际本地浏览器入口验证。对外公开来源仅在明确批准时从本机手工启动。
5. MySQL 批次保持一次连接/事务边界、参数化写入和有限重连；连接凭据、Cookie、原始完整响应和导出数据不得进入 Git、日志或任务文档。
6. 不修改未归属的工作区改动；不增加新的手工旁路、第二套 schema、第二份 staging 或第二种发布路径。
